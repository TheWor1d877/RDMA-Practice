# 错误总结

从 Soft-RoCE 到云上踩过的坑，每条按 docs/3 验收要求的格式写：现象、根因、怎么解的。云上新增的坑跑完补进这里，这份文件是活文档。

### RTR 迁移返回 EINVAL（errno=22）

**现象**：`ibv_modify_qp` 迁移 INIT→RTR 时返回 EINVAL，错误码 22，报错不指明是哪个字段有问题。

**根因**：`attr.ah_attr.is_global` 漏设。IB 网卡靠 LID 寻址，RoCE 没有 LID，地址向量只剩两条寻路途径：`dlid` 和 GRH 全局路由段，两条都空时 rxe 驱动校验不过，直接 EINVAL。RoCE 下必须置 `is_global = 1`，`grh.dgid` 填对端 GID，`grh.sgid_index` 选本端 GID 表项。

**怎么解的**：`ibv_modify_qp` 迁移前把 attr 的关键字段打印出来，逐个对着 docs/2 的 RTR 字段清单查。这个错教会一件事：**EINVAL 不指明字段，靠迁移前打印参数、迁移后查返回值的纪律定位**，三段迁移的每一处都要这么打日志。

### RTR 迁移返回 ETIMEDOUT（errno=110）

**现象**：RTR 迁移这次没报 EINVAL，改成 ETIMEDOUT。换成有线网或者换一次 Wi-Fi 就时好时坏。

**根因**：笔记本 Wi-Fi 开了 IPv6 隐私扩展（RFC 4941），接口真实的 link-local 地址是随机生成的（`fe80::bbcf:802a:80f1:bba3` 这种）；而 rxe 设备的 GID 是按网卡 MAC 经 EUI-64 推导的（`fe80::de90:9ff:fe63:5e2`）。GID 表里登记的地址没人持有，迁移时 NDP 邻居解析查不到 MAC，等超时。云上网卡不开隐私扩展，这个错只在笔记本 Soft-RoCE 上常见。

**怎么解的**：给 NDP 加静态映射，跳过解析：

```bash
sudo ip neigh replace fe80::de90:9ff:fe63:5e2 lladdr dc:90:09:63:05:e2 dev wlp4s0
```

（GID 的 EUI-64 部分和 MAC 对得上：`dc:90:09:63:05:e2` → `de90:9ff:fe63:5e2`。）重启或换网络后映射失效，报 ETIMEDOUT 先想这一条。

### rping 报 rdma_resolve_route: No such device

**现象**：`rping -c -a 127.0.0.1` 报 `rdma_resolve_route: No such device`，但 rping 服务端明明起来了。

**根因**：rdma_cm 拿到目标 IP 后按**路由表**把 IP 映射到 RDMA 设备。`127.0.0.1` 属于 `lo` 网卡，rxe0 绑在 `wlp4s0` 上，映射不到就报这个错。

**怎么解的**：客户端地址写本机实际网卡 IP（`rping -c -a 192.168.51.191`）。注意区分：stage2 模块的 TCP 控制面用 127.0.0.1 没问题——那是内核网络栈的普通 TCP，不经过 rdma_cm 的设备映射。

### ibv_reg_mr 失败：memlock 上限

**现象**：server 预注册 8 个 1MB 槽位，`ibv_reg_mr` 返回失败。

**根因**：`ulimit -l` 只有 8MB，锁页配额装不下 8×1MB 的注册内存。

**怎么解的**：本机冒烟用 256KB 槽位（`run_smoke.sh` 里已写死）；云上放开限制再跑 1MB 槽位：

```bash
sudo sh -c 'echo "* soft memlock unlimited" >> /etc/security/limits.conf'
sudo sh -c 'echo "* hard memlock unlimited" >> /etc/security/limits.conf'
```

### post_recv 返回 EINVAL（rc=22）

**现象**：server 在 `Connect` 之前挂第一条 recv WR，`ibv_post_recv` 返回 EINVAL，server 直接退出；对端 client 随后报 `transport retry counter exceeded`——对端没了，所有 WR 重试耗尽。

**根因**：QP 还在 RESET 态。`ibv_post_recv` 要求 QP 至少处于 INIT 态，RESET 态直接 EINVAL。

**怎么解的**：recv WR 挪到 `Connect`（内含 INIT→RTR→RTS）之后立刻挂。时序不亏：client 发第一条 SEND 前要先填 64KB payload，本端建完链立刻挂 WR 赶得早；极端情况撞上 RNR NAK，发送端 `rnr_retry=3` 兜底。

又一条 EINVAL，和 RTR 那条同一个教训：EINVAL 不告诉你原因，要对照 QP 状态机的时序排查——这次是状态不对，上次是字段没填。
